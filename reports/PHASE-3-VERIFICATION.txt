3. TEST METHOD (WHAT ACTUALLY RAN)
----------------------------------
Runtime: real Chromium through the managed Playwright install
         (/opt/appjet/browser/node_modules/playwright), headless.
Server:  python3 -m http.server on 127.0.0.1:4173 serving the repository root.
         Port 4173 as required. The server was started and stopped by the harness.
Driver:  a single verification script, /tmp/verify-ui.cjs, kept outside the
         repository so it cannot affect the shipped site or the file inventory.
Viewport: 1280 x 900 for the gameplay, save and keyboard runs.

The script does not re-implement the game. It loads the shipped files exactly as
the page loads them:

  assets/js/signal-path-core.js      (the real rules)
  arcade/data/signal-path-levels.js  (the real level data)

through a Node `vm` context, parses the levels with the shipped parser, and solves
each level with a breadth-first search over the shipped movement and gating rules.
The resulting move sequences are then replayed on the real page using real
keyboard presses (ArrowUp / ArrowDown / ArrowLeft / ArrowRight), and the state is
read back from the page's own DOM (its data- attributes) rather than from the
script's expectations.

This means the routes are solver-verified and the execution is genuinely
through the browser interface — not a rules-only simulation.

7. ITEM D — MALFORMED SAVE IN A REAL BROWSER PROFILE
----------------------------------------------------
Method: a fresh browser context was given the Arcade key
wrong-script.arcade.signal-path.v1 containing the deliberately broken value
"not json at all" before the page loaded (a real localStorage write in a real
profile), then the page was opened.

Result: PASS, across four checks.

  1. Load — the save note reported that progress could not be read, stated that
     nothing has been deleted, and pointed the player at the reset control. The
     game started safely at level 1. The stored raw value was still exactly
     "not json at all".

  2. Play — level 1 was completed while the stored value was broken. The level
     completed normally, and the stored raw value was STILL "not json at all":
     the broken value was not overwritten by play.

  3. Reload — the warning was still shown and the game still started at level 1.
     The failure was not silently swallowed into a fresh start.

  4. Explicit reset — the reset control opened a confirmation panel first; only
     after confirming was the key removed. The default note ("Progress is saved
     in this browser only") returned, the game sat at level 1, and a "Progress
     reset" status appeared.

This closes the Phase 3 limitation that malformed-save recovery had only been
proven at rules level.

11. THE FAILED FIRST ATTEMPT (KEPT IN THE RECORD)
-------------------------------------------------
The first run of the harness (call-51289c6a) reported 10 passed and 16 failed.
The cause was in the harness, not the application: the page renders level names
in uppercase through CSS text-transform, so comparing the displayed text to
"Relay Room" failed on "RELAY ROOM". Because that assertion came before the key
presses, the level was never completed, so the following "Next level" clicks
waited on a button inside a still-hidden result panel and timed out.

One further attempt to re-run it as a formal retry was rejected by the tooling
because the failed check was not yet registered in the checkpoint; it executed
nothing.

The correction was confined to the harness: case-insensitive comparison of
displayed text (an eq() helper and /i flags). Routes, selectors, viewports and
expected values were unchanged. The application code was not touched, and no
assertion was weakened — the corrected run asserts the same state it always
intended to assert.

The already-passing checks in that first run (sealed beacon, restart, all four
malformed-save checks, reduced motion, keyboard traversal, keyboard activation,
no console errors) were reproduced identically in the final run.
