================================================================================
6. THE CENTRAL QUESTION
================================================================================

The Creator Studio, as described on the Lobby card, is "tools for making your
own scenes in this universe". The long-standing platform rule, stated in the
Phase 4 and Phase 5 instructions and repeated in the Archive's own framing, is
that member-created work must be submitted and reviewed before publication.

Those two statements together describe a system with four parts:

  1. somewhere for a person to compose or submit work
  2. somewhere to store it before review
  3. a way to identify who submitted it, and to keep it private until
     approved
  4. a review step, and a publication step that is separate from submission

The project as it stands has none of these and cannot have them:

  - there is no server, so there is nowhere to store a submission
  - there is no identity, so there is no way to keep an unapproved
    submission private to its author, and no way to attribute work
  - there is no review queue, so "reviewed before publication" would be a
    claim with nothing behind it
  - there is no database, so nothing survives the browser

A static site can fake every one of those things, and each fake would be a lie
of exactly the kind this project has spent six phases avoiding: a form that
says "submitted" and stores nothing, a "pending review" badge for a queue that
does not exist, a profile for an account that cannot be created.

This is the finding that shapes Phase 7. It is not a technical obstacle to be
worked around; it is a product boundary. The honest options are set out below.

================================================================================
7. SCOPE OPTIONS
================================================================================

OPTION A - A READ-ONLY STUDIO (recommended)

  Build /creator-studio/ as a room that documents how work is made in this
  universe and states plainly that submissions are not open.

  Contents: what the studio is for; the published format that stories and
  games in this universe actually follow, using the real files as the
  reference; the editorial standard a submission would have to meet; an
  honest statement of what does not exist yet, with no date promised.

  Fits the architecture exactly: page, stylesheet, data module, renderer, no
  storage, no network, no forms. Adds no key and touches no existing one.
  Closes the last "Coming in a later phase" destination without pretending.

  Risk: a studio with no making in it may read as thin. Mitigated by making it
  genuinely useful - the scene and level formats are real, documented in the
  README, and have never been presented to a visitor.

OPTION B - READ-ONLY STUDIO PLUS AN OFF-SITE SUBMISSION ROUTE

  As Option A, plus a route for sending work in - for example a mailto link or
  a third-party form service.

  Honest, but it introduces something the project has so far refused: either a
  third-party request from the page, or a public contact address, and with it
  personal data arriving in someone's inbox with no policy, no retention rule
  and no review process to receive it. It also breaks "no third-party
  requests" in the README.

  Not recommended for this phase. If it is ever wanted, it needs its own
  review covering data handling, not a line in a build prompt.

OPTION C - A REAL STUDIO: BACKEND, ACCOUNTS, SUBMISSION, MODERATION

  The full system. This is what the long-term product rule actually implies,
  and it is the only option that could ever make "make your own scenes"
  literally true.

  It requires a server, a database, authentication, private storage for
  unapproved work, a moderation interface and a publication pipeline. It is a
  different architecture from the one this project has, and it cannot be
  delivered as one incremental static phase. It also brings obligations the
  current project has none of: personal data, account recovery, abuse
  handling, and a reason for someone to trust the site with their work.

  This is a decision for the owner, not a scope the developer can adopt. It
  would need its own planning document, its own phases, and probably its own
  hosting.

RECOMMENDATION

  Phase 7 = Option A. Defer Option C until it is chosen deliberately, with
  Option B rejected unless a data-handling review says otherwise.

  Rationale: Option A finishes the universe as it was described in Phase 1,
  keeps every promise the current architecture can keep, and tells the truth
  about the one it cannot. Option C can then be planned on its own terms
  rather than smuggled in as "Phase 7".

9. PROPOSED CONTENT MODEL
================================================================================

Following the established pattern, content is data and the renderer only draws
it. A shape in the spirit of the other rooms:

    {
      parts: [
        { id, title, eyebrow, paragraphs: [ ... ], note?: string }
      ],
      format: { title, intro, entries: [ { id, name, kind, summary,
                 fields: [ { name, purpose } ], source } ] },
      standard: { title, intro, rules: [ { id, heading, body } ] },
      notYet: { title, intro, items: [ { id, label } ] }
    }

Rules for the renderer, consistent with every room since Phase 2:

  - createElement and textContent only; no innerHTML for content
  - ids double as deep links (/creator-studio/#<id>) with the same
    unknown-fragment recovery the Archive uses, including the Phase 6A rule
    that only one target is marked at a time
  - no filters unless they earn their place; four parts need a jump list,
    not a filter bar

================================================================================
10. ISOLATION AND SAFETY RULES
================================================================================

  - No storage: no localStorage, sessionStorage, IndexedDB or cookies. No save
    key, and no reading of tws, wrong-script.story.the-ninth-bell.v1 or
    wrong-script.arcade.signal-path.v1. The three key strings must not appear
    in the room's scripts at all.
  - No network: no fetch, no XHR, no external asset, no analytics.
  - No personal data: nothing asked for, nothing stored, nothing displayed.
  - No identity: no account, profile, avatar, handle or member name.
  - No user-generated content, and therefore no moderation surface.
  - Attribution: "The Wrong Script Studio" only.

These are the same rules the Gallery, Social Room and Archive were built to,
and the existing static verifiers check them by scanning source. Phase 7's
verifier should reuse that check rather than invent a new one.

  R1  A studio that cannot accept work may feel empty or disappointing.

      tools/verify-social-room.js already does for one string.

  R5  The Lobby card's "Phase 7" badge and the hero eyebrow drift out of date
