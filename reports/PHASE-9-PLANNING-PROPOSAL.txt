1.3 Code shape

Plain HTML, CSS and vanilla JavaScript; no framework, no bundler, no backend, no
external assets. Roughly 4,066 lines of JavaScript and 3,875 lines of CSS across
17 JS and 7 CSS files, plus 11 HTML pages.

A consistent layering has emerged, and it is the project's main architectural
asset:

  - Content as data      stories-index.js, arcade-games.js,
                         signal-path-levels.js, gallery-exhibits.js,
                         social-room-content.js, archive-content.js,
                         creator-studio-content.js, the-ninth-bell.js.

                         createElement/textContent.

                         room's identity.
  - Per-room navigation  the same <nav id="site-nav" aria-label="Platform">
                         markup, hand-written into every page with relative
                         paths.

2.3 Structural debt worth naming now

  1. Navigation is duplicated in eleven HTML files. Adding a room means editing
     every page by hand, and two UI suites encode expected nav behaviour. This is
     the highest-probability source of a future silent drift bug.
  2. No single test entry point. Nine suites must be run in three groups; nothing
     guarantees all of them run before a phase closes.
  3. No suite for the Lobby, Stories or the film. The rooms with the most history
     have the least automated coverage.
  4. The "add a story" and "add a game" recipes are untested as recipes. The
     engine's per-story parameterisation has been exercised with exactly one
     story.
  5. CSS has no shared token layer beyond lobby.css. Seven room stylesheets
     (452-810 lines each) each restate palette and rhythm; drift is already
     possible and will compound.
  6. No 404 page and no metadata beyond <title>/description per page. Deep links
     are hash-based, so this is polish, not breakage.
  7. No performance budget. Nothing measures page weight; nothing would notice a
     doubling.

2.4 Content scale

One story, one game, eight exhibits. Every structural claim in the README about a
growing library is currently a promise tested once. This is the single biggest
product risk: the platform looks like a library but has never held a second book.

2.5 Documentation drift

README phase list ends at Phase 7; Lobby copy and footer say "Phase seven"; the
discovery strip's three sample cards describe things that "will" exist. None of
this is dishonest - all of it is now stale, and stale copy on the front door is
exactly what this project has been careful to avoid.

3. RECOMMENDED NEXT DEVELOPMENT DIRECTION
--------------------------------------------------------------------------------

Recommendation: Phase 9 = "Depth and Proven Modularity"

Add one new interactive story and one new game, using only the documented recipes
and without restructuring the engine; close DEF-01 and DEF-03; retire the Lobby's
placeholder strip and stale milestone copy; and add the two missing pieces of
verification infrastructure (a nav-parity check and a single verify-all entry
point).

Why this, and not something else:

  1. It tests the platform's central claim. Every future phase depends on
     "content is data; adding a room is mechanical". That claim has been
     exercised once, on the content that defined it. A second story and a second
     game prove or disprove it cheaply, while the code is small.
  2. It is the lowest-risk way to grow. No new architecture, no new storage keys
     beyond the two namespaced ones, no new dependencies, no backend decision
     required. Every failure mode is local and reversible.
  3. It fixes the only defects that exist while the code is fresh in context, and
     it clears the front-door placeholders - the two things a returning visitor
     would actually notice.
  4. It buys information for the big decision. The participation question
     (accounts, submissions, moderation) is not a code phase; it needs an owner
     decision about hosting and architecture. Phase 9 does not block on it and
     produces the evidence that decision needs: what a real library costs to
     maintain.

Evidence rules: every row labelled PASS / FAIL / NOT TESTED / CODE REVIEW ONLY /
BLOCKED / NOT APPLICABLE. Emulation is never reported as device testing;
automated structural checks are never reported as screen-reader testing; a
zero-package scan is never reported as a security certification. Historical
failures are preserved, not rewritten.

What this environment cannot close, and should not pretend to: Firefox, WebKit,
Edge, physical devices and every assistive technology. The cheapest genuinely new
accessibility evidence available here is Chromium zoom/reflow at 200% and 400%,
forced-colours mode and OS text scaling - recommended as a T2 extension whenever
the owner next authorises corrections.
