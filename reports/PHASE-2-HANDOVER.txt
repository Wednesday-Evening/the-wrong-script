================================================================================

Phase 2 opens the first real room past the Lobby: a working story library at
/stories/, containing one complete original interactive story, "The Ninth Bell",
readable end to end through five distinct endings.

Three things exist that did not before:

  a) A Stories library page with its own visual identity (night-shift reading
     room: near-black surfaces, deep red rules, parchment text, muted gold
     furniture) that lists only experiences that actually work.

  b) A complete original story with a flag-driven scene engine, four hub
     "watches" of night, five endings, restart/replay, and a namespaced,
     validated save that is entirely separate from the film's save.

     history so a scene can be deep-linked and the browser Back button has
     something sane to return to, and defensive validation when reading the
     existing "tws" save so a corrupt or legacy value cannot destroy progress.

The original film was NOT rewritten, renamed or restructured. Its scenes,
dialogue, puzzles, routes, three endings, post-credits sequence, replay
behaviour and localStorage key "tws" are all intact.

5. THE NEW STORY — PREMISE, ROUTES, CHOICES, ENDINGS
================================================================================

TITLE:    The Ninth Bell
SETTING:  Halversen Light, a rock lighthouse, one night, in the era of paper
          logs and oil.
PREMISE:  You arrive as the relief keeper. Hask, the keeper you are replacing,
          gives you three rules: keep the light, write what happens in the log,
          and if the bell starts, count to eight and stop counting. The bell
          stands out past the causeway, and the town pays rent on it.
          Nobody has counted to nine.

This is deliberately not a romance, and deliberately not a haunted-house jump
scare. It is a story about a rule you inherit and a record you are asked to
keep — and about what the record is hiding.

STRUCTURE
  The night is divided into four "watches". The tower hub shows the hours left
  and offers the same five doors each visit: the log room, the lamp room, the
  boathouse, the causeway, and "turn in". Visiting a door spends a watch and
  usually sets a flag. After the fourth watch the hub stops offering doors and
  the night resolves — so there is no way to wander forever, and no dead end.

  Flags set by the rooms gate what you can do at the bell:
    rule      — you know what Hask's rules actually mean
    close     — you have read the last page of the log
    rope      — you know where the tarred rope is
    chapel    — you have seen how the bell's frame is pinned
    habit     — you have read the 1962 entry
    ines_trust, shore_truth, quiet — the shore-side threads

FIVE ENDINGS (all reachable, each a distinct conclusion, none a loop)
  1. The Hour Given   (uneasy)       Ring the tenth from the shore frame and pay
                                     the bell what it is owed.
  2. The Silence      (bittersweet)  Cut the bell down and end the arrangement.
  3. The Ledger       (hopeful)      Dark the lamp and ring from the point, after
                                     reading the last page.
  4. The Habit        (uneasy)       Keep the light, count to eight, go to bed —
                                     the rule holds for another year.
  5. Relief           (quiet)        Reach the morning without ringing anything.

  Choice requirements are visible in the writing, not hidden: a choice only
  appears when you have actually learned the thing it depends on, and each
  choice carries a short note explaining what it means. There are no purely
  cosmetic choices dressed up as meaningful ones.

  On reaching an ending the panel names it, gives a one-line reflection, offers
  READ IT AGAIN, BACK TO THE STORIES and THE LOBBY, and updates a per-browser
  "ENDINGS FOUND: n OF 5" counter. Discovery is the replay hook — not an
  endless loop.

ACCESSIBILITY AND TONE
  Teen-appropriate. No gore, no sexual content, no self-harm, no real-world
  dangerous instruction. Violence is implied off-page at most. Sound is off by
  default and there is no audio autoplay. Text and choices reflow at 390px with
  no horizontal scrolling; choice numbers are text, not emoji.

6. STORY DATA / SCENE STRUCTURE (how Phase 3+ extends this)
================================================================================

Content and rendering are separated:

  stories/data/the-ninth-bell.js
      window.TWS_STORIES = {
        meta:   { title, subtitle, blurb, genre, minutes, saveKey, ... },
        start:  'arrival',
        scenes: { arrival: {...}, tower: {...}, ending_hour: {...}, ... }
      }

  Scene fields actually used:
      title       string, shown as the scene heading
      chapter     optional section label ("I — The Relief")
      lines       [ { who, text } ]   who may be a character name or narrator
      choices     [ { label, note, to, requires, set } ]
                    requires: { flag: 1 } — choice hidden until satisfied
                    set:      { flag: 1 } — flags written on choosing
      hub         { budget: 4 } — visit-limited hub that resolves on exhaustion
      ending      { name, kind } — marks a terminal scene and its tone label

  assets/js/story-engine.js
      Reads the data, owns state, validates the save, renders through the
      [data-*] mount points, and never contains story prose.

  Adding a second story therefore means: a data file, a registry entry in
  stories-index.js, and a reader page that mounts the same engine. No engine
  change and no CSS change should be needed.

  Saved state per story is namespaced:
      wrong-script.story.the-ninth-bell.v1
  The version suffix allows a future data change to invalidate its own saves
  without touching any other story or the film.

8. BACK / FORWARD SUPPORT — WHAT WAS DONE AND WHAT WAS TESTED
================================================================================

IMPLEMENTED
  - syncHash() writes the current scene id into location.hash. The first draw
    uses history.replaceState (so the entry you arrived on is rewritten rather
    than duplicated); later scene changes use history.pushState.
  - syncHash() is called from the scene transition path only. Cosmetic updates
    (sound toggle, calm toggle, reel indicator) do NOT push history entries, so
    Back does not walk through every trivial UI change.
  - A popstate listener reads the hash and restores that scene, so Back and
    Forward move between scenes rather than leaving the film.
  - On load, a hash present without a matching saved run is cleared with
    replaceState, so a stale or hand-edited deep link cannot hijack a real save.

TESTED
  PASS — Deep-link restore: navigating directly to /film/#cast and asserting the
         scene chrome (#bar) became visible. The film rendered the cast scene
         from the hash instead of starting at the title card.
  NOT TESTED — Browser Back / Forward button traversal through several scenes.
         The managed browser harness used here can navigate, click, type and
         assert, but it does not expose browser-history traversal, so I did not
         claim a Back/Forward walk-through I could not run. The push/replace
         policy and the popstate restore path are CODE REVIEW ONLY.

  Note on an earlier failed attempt: I first tried to assert the URL changed
  after clicking SKIP INTRO. That assertion waits for a page load event, and a
  hash change fires none — the test instrument was wrong, not the film. The
  deep-link test above is the correct check and it passed.

9. SAVE VALIDATION / VERSION HANDLING — WHAT WAS DONE AND WHAT WAS TESTED
================================================================================

IMPLEMENTED in the film's load()
  - JSON parsing wrapped in try/catch; a malformed value no longer throws
    through the scene renderer.
  - Shape validation: the parsed object must look like a run (scene id, flags,
    counts). Anything else is treated as absent.
  - Legacy tolerance: an older save with no version field is still accepted and
    upgraded in memory — a valid old save is never discarded merely because a
    version field is missing.
  - Fail-safe: on unreadable or malformed data the film starts a fresh run in
    memory and does not write over the stored value until the player actually
    plays, so a bad read cannot silently destroy a good save.

TESTED
  NOT TESTED — I did not run a browser test with a crafted legacy save and a
         crafted malformed value. Doing that safely requires writing to "tws",
         and I was not willing to risk a real player's save (or the verification
         environment's state) for a hardening check in this phase.
  CODE REVIEW ONLY — the try/catch, shape guard and legacy acceptance path.

  Recommended follow-up: a dedicated test that seeds "tws" with a legacy object
  and a broken string in an isolated browser profile, asserts CONTINUE works on
  the legacy value and that the broken value starts clean without overwriting.

14. TECHNICAL DECISIONS THAT AFFECT LATER PHASES
================================================================================

  - Data/engine split is the extension contract. Phase 3+ adds a story by adding
    a data file, a registry entry and a reader page. If a future story needs new
    scene behaviour, extend the engine's scene schema rather than forking it.
  - One CSS file per experience (lobby.css, stories.css, the film's inline
    styles) keeps experiences independent. Avoid a global stylesheet that all
    three must share.
  - Save keys are namespaced per story and versioned. Do not introduce a shared
    "platform save" object: it would couple every experience to every other and
    make one bad migration destroy all progress at once.
  - The film's "tws" key is treated as a frozen external contract. Nothing new
    may read or write it except the film itself (and the Lobby's read-only
    CONTINUE strip, which already existed).
  - Static hosting only: every route is a directory index.html. A future phase
    that wants client-side routing must keep deep links working without a
    server rewrite, or the static hosting model breaks.
