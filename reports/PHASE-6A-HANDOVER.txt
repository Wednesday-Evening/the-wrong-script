2. ROOT CAUSE (F1)
--------------------------------------------------------------------------------

assets/js/archive.js, resolveHash(), before this pass:

    if (!id) { return; }

    var target = document.getElementById(id);
    var isSection = SECTIONS.indexOf(id) !== -1;

    if (target && (isSection || target.closest('.file, .collection, .discovery'))) {
      target.classList.add('is-target');
      return;
    }

The class was added and never removed anywhere in the codebase. A search for
"is-target" returned only that add call, the ".is-target" rule at
assets/css/archive.css:493 (a gold inset bar: box-shadow: inset 2px 0 0
var(--gold)), and report prose. There was no removal call.

Consequence: the marker latched for the lifetime of the document. Each fragment
visit added another marked node, so after visiting Completed Files and then
Discoveries both carried it. Back and Forward re-run resolveHash() and added
again, so an earlier marker survived the return trip. A reload cleared it only
because the DOM is rebuilt, which is why the Phase 6 verification pass saw a
clean state after a fresh load (B10) but accumulation within a session (B7/B8).

--------------------------------------------------------------------------------
3. THE CORRECTION
--------------------------------------------------------------------------------

assets/js/archive.js, resolveHash(), after this pass - one loop, inserted before
the fragment is resolved:

    if (note) {
      note.hidden = true;
      clear(note);
    }

    /* Phase 6A (F1): the marker belongs to whatever the fragment addresses, so
       any earlier target is unmarked before this one is resolved. An empty or
       unknown fragment therefore highlights nothing, exactly as a reload of the
       same URL would. */
    var marked = document.querySelectorAll('.is-target');
    for (var i = 0; i < marked.length; i += 1) {
      marked[i].classList.remove('is-target');
    }

    if (!id) { return; }

    var target = document.getElementById(id);
    var isSection = SECTIONS.indexOf(id) !== -1;

    if (target && (isSection || target.closest('.file, .collection, .discovery'))) {
      target.classList.add('is-target');
      return;
    }

No other line of application code changed. No CSS change was required: the
".is-target" rule at assets/css/archive.css:493 is untouched and now simply
applies to one node at a time.

3.1 DESIGN DECISION - where the clear happens

F1 sketched the clear inside the valid-target branch. This pass clears once per
resolveHash() run, before the fragment is resolved. For every valid navigation
the outcome is identical, and requirement 1 ("clear previous markers before
marking the newly resolved valid target") is satisfied. The difference is the
unknown and empty fragment case: nothing is highlighted.

Rationale: an unknown fragment addresses no section or entry, so highlighting a
previous one while the recovery note says "No entry is filed under X" would be
contradictory. Clearing makes in-session behaviour agree with a reload of the
same URL, which already showed no marker. This is a deliberate decision, stated
here so it can be reviewed, and it is asserted by the new tests.

  PASS  an unknown fragment clears the previous marker               [[]]

Method: a fresh cross-document load of /archive/ (via / first, so the document is
genuinely new). The first jump is a real click on the page's own
"Completed Files" jump link; subsequent targets are reached by assigning
location.hash, which is the same hashchange path the jump links and entry links
use. After each navigation the assertion waits for the settled state - exactly
one node with the expected id, or zero for the unknown case - before reading the
marker list, so a stale marker cannot be mistaken for the correct one. Back and
Forward use the browser's own history.
