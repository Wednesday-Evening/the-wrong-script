3. DELIVERED SCOPE — WHAT THE SOCIAL ROOM IS
--------------------------------------------------------------------------------
A read-only, curated room at /social-room/ with four boards:

  The Noticeboard       4 entries: studio notes, universe updates, featured
                        discoveries and editorial notices.
  The Open Questions    4 entries: prompts to think about, each linked to the
                        work it came from. No reply box, no thread.
  The Gathering Board   4 entries: invitations, ideas and worked examples,
                        labelled as such. Nobody is claimed to have joined.
  What's Happening      6 entries: the four live destinations marked
                        "Open now", The Archive and The Creator Studio marked
                        "In preparation".

Each entry carries an explicit kind label (Studio note, Update, Featured
discovery, Editorial, Open question, Invitation, Idea, Example, Listing) so the
reader always knows what they are reading. The four What's Happening statuses
are editorial labels, not live event data, and the board says so in a footnote.

The room states its own limits in plain words inside The Noticeboard:
"The room has no likes, no visitor count and no ranking. It is a wall you walk
along, not a feed you keep up with."

Nothing in the room is interactive except navigation. The only <button> on the
page is the shared `#nav-toggle`; there is no form, input, textarea or select.

6. CONTENT MODEL
--------------------------------------------------------------------------------
`assets/js/social-room-content.js` publishes one object:

  window.SOCIAL_ROOM = {
    version: 1,
    title, lede, footnote,
    areas: [ { id, label, eyebrow, lede, footnote, entries: [ ... ] } ]
  }

Entry shape:
  { id, kind, title, body, link: { label, href } }   (What's Happening adds
                                                      `status`)

The renderer reads this data and builds DOM with createElement and
textContent only. There is no innerHTML anywhere in the room's scripts, so no
content string can become markup or script. Every internal link was checked
against the file system by the static suite; there are no external URLs,
protocols or data: references in the content.

7. READ-ONLY BEHAVIOUR AND WHAT IS NOT IMPLEMENTED
--------------------------------------------------------------------------------
Implemented: curated reading, four boards, jump list, deep links to boards and
entries, honest recovery for unknown ids, responsive layout, keyboard and touch
operation, reduced-motion support.

Not implemented, and not pretended: accounts, profiles, sign-up, login, posting,
comments, reactions, voting, messaging, uploads, member submissions, event
attendance, notifications, analytics, backend, database, moderation. There is
no form and no storage call, so there is nothing that could look like a
submission path. The page states that this first version is curated.

8. TECHNICAL NOTES
--------------------------------------------------------------------------------
- The jump list is four real anchors. The marked item is recomputed from scroll
  position: the current board is the last one whose heading has crossed 45% of
  the viewport height. This is rAF-throttled and runs on scroll, resize and
  hashchange, so the marker agrees with the board at the top of the screen after
  a click, a deep link or a manual scroll, at any width.
  (An earlier IntersectionObserver implementation could mark a board the page
  was only passing; see section 10.)
- A deep link such as /social-room/#whats-happening moves focus to that board's
  heading so keyboard and screen-reader users land where they asked.
- An id that does not exist shows a visible note naming the missing id and
  offering "Start at The Noticeboard", instead of failing silently.
- The room makes no network request of its own: no fetch, XHR, beacon or
  websocket. All CSS, JS and imagery are local files.
- No shared code was modified. The five destination pages each received one
  list item in their existing nav markup; the Lobby received one card state and
  one link.

E. CHRONOLOGY OF FAILED CHECKS AND THEIR RESOLUTION
   Earlier failures are retained here rather than replaced, so the record is
   complete. All three were resolved and rerun. The "revision N" labels below
   are the internal verification counters used in the session check record, not
   git commits; see section 17.

   E1  Revision 13 — static suite FAIL (2 of 24).
       "every existing page links to the Social Room: film/index.html has no
       link to ../social-room/" and "the film file is untouched by this phase:
       the film nav does not mention the room".
       Cause: wrong assumptions in the check, not a defect. The film has no
       platform nav (it is a full-screen experience), and the room marks itself
       current with href="./" following the Lobby's convention rather than an
       absolute path. The two assertions were replaced with accurate ones: the
       film carries none of the room's code, and film/ has no diff against HEAD.
       Resolution: rerun at revision 16 — 26 of 26 PASS.

   E2  Revision 16 — browser suite FAIL (8 of 35).
       Causes, all in the check: (a) the selector `#jump .jump-list a` matched
       nothing because `#jump` is itself the <ul>, so its links are direct
       children; (b) the h1 assertion expected "Social Room" but the room's h1
       is the tagline "A room with the lights on"; (c) a banned-word scan
       matched the word "likes" inside the honest disclaimer "The room has no
       likes, no visitor count and no ranking"; (d) the storage check timed out
       on the same broken jump selector.
       Resolution: selector corrected to `#jump a[data-area]`, the h1 assertion
       corrected to the real heading plus a document-title check, and the
       banned-word scan replaced with real social-proof patterns
       (N likes / N followers / N comments / members online / joined by /
       trending now / N attending) plus positive assertions that the disclaimer
       is present. Rerun at revision 17.

   E3  Revision 17 — browser suite FAIL (1 of 35).
       "the jump list moves between boards at 390px phone: aria-current sits on
       ["open-questions"]".
       Two genuine causes:
       (a) The application used an IntersectionObserver whose record order is
           not deterministic, so the marked link could disagree with the board
           at the top of the screen. This was an application defect, not a test
           artefact. It was fixed by replacing the observer with the
           deterministic scroll-position rule described in section 8.
       (b) The check sampled the page mid-way through the smooth hash scroll,
           so it read a board the page was only passing through. The check now
           waits for the scroll position to hold still before asserting.
       Resolution: rerun at revision 19 — 35 of 35 PASS at both widths.
